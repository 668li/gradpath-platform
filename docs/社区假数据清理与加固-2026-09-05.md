## 07 第一性原理 — 拆回最底层

**已确认、无法绕开的基本事实**：
1. 社区的本质价值 = 真实用户的真实交互；信任是唯一护城河（劝退卡战略的同源逻辑：造假错一次，十倍代价）。
2. 生产社区真实用户内容 = 0。所谓"社区"是 2187 条脚本注入内容的空壳。
3. 假数据有四个持续注入源：种子脚本（run_all_seeds 仍调用 seed_community）、一次性注入脚本、归档生成器、crawlers/real_data 内置生成器。
4. 用户已拍板：社区只能有用户自己发的信息。

**被推翻的惯性假设**：
- ❌"冷启动需要假内容撑门面" → 冷启动空态是诚实的，假热闹是欺诈（581 假进面线事故已验证过一次）。
- ❌"爬来的真实内容放在社区、加个 external 标注就够了" → 详情页作者兜底"匿名用户"，用户无从分辨；同表同池是事故温床。
- ❌"前端 tab 分池过滤就是隔离" → 表层补丁。数据层同池 + 种子随时重灌 + 灵感案例组件照常直通表，隔离形同虚设。

**原方案只在修补表面的部分**：此前所有治理（前端 source_platform 过滤、审核字段、主题门禁）都作用在"流出端"，而事故的根在"流入端"（脚本直写 approved）+ "向量层残留"（语义检索复活已删内容）。

**从基本事实重新推导的路径**（本次已执行）：
1. 数据层物理清除：社区 5 表清零 + 孤儿向量清除（源行不存在的向量一律删）。
2. 流入端封堵：删 seed_community/seed_posts；4 个纯造假生成器 SystemExit 硬闸；run_all_seeds 摘除社区调用并如实改 docstring。
3. 展出端诚实化：外部经验 tab、硬编码"热门话题"、Trae 灵感案例全部移除；空态=引导发帖。
4. 结构性免疫：社区 UI 只渲染 `source_platform=user`，即使未来外部内容再入表也不会出现在社区。

**成立的前提**：删除前有表级备份；0 真实用户内容受损（已实证）；爬虫脚本不删（用户红线，只闸不删）。

**验证第一步**：删除后重打三个社区 API（posts/public、experience-posts、qa）→ 200 + 空列表（已通过，见冒烟记录）。

## 06 专家会诊 — 三个互补视角互相质疑

**产品/增长视角**（社区怎么活）：
- 重定义：清空后的问题不是"内容少了"而是"版面空了"。推荐：空态卡引导发帖（已有 EmptyState"成为第一个分享经验的人"）；真实增长靠决策引擎/测评结果转成"发布我的疑问"的动线。最大风险（别的视角会忽略）：社区页面在推广期看起来"死"。改变判断的证据：若推广后发帖转化率显著低于行业冷启动基准，考虑用"官方数据卡"填充版面（明确署名官方，绝不伪装 UGC）。

**数据工程视角**（结构怎么立）：
- 重定义：这不是删数据问题，是**所有权问题**——experience_posts 一张表装两种所有权的内容（用户 vs 平台搬运），任何过滤都是补丁。推荐：社区表语义收紧为"仅用户内容"；外部真实内容若将来恢复供给，导入资讯表（t_external_research_item/data_sources）而非社区表。最大风险：孤儿向量这类"派生层残留"——**本轮已把向量层纳入清理**，并确立规则"无活源即删"。改变判断的证据：若发现还有第三方消费 experience_posts 的 external 行（如 AI 管家引用外部内容），需要先迁移再清。

**安全/风控视角**（假数据怎么再进来）：
- 重定义：删假数据≠防假数据；真威胁=脚本直写 + 未来垃圾注册机发帖。推荐：审核门保持（经验贴/问答默认 pending）；讨论帖 posts 无发帖前审核但有举报+hidden 通道，本轮不动（过度审核杀真实互动）；生成器硬闸；每轮清理必须带上派生层（向量/缓存）。改变判断的证据：若出现注册即灌帖的 spam 模式，posts 需加频率限制或审核。

**互相质疑后的共识与分歧**：
- 共识：数据清零+流入端封堵+向量层纳入是底线，三视角无异议。
- 真分歧：外部真实内容（知乎/考研论坛 40 条）删不删。产品说可惜、工程说同池必再犯、安全说无所谓 → 提交钢人论证裁决。
- 分歧背后的假设：产品假设"标注可被用户看见"（生产详情页不成立）；工程假设"表语义必须单一"（被接受）。

**综合方案**：全清 + 封堵 + 结构免疫（即本轮执行）。适用条件：社区真实内容=0 时无痛；最大风险=冷启动版面空（产品视角已给退出条件）；退出条件=若真实发帖率长期为 0 且官方数据卡能诚实填充，改走官方供给方案；第一步行动=删除+部署+冒烟（已完成）。

## 附：缓存序列化 bug（清假数据顺手揪出的生产级缺陷）

- 现象：`/api/kaoyan/experience-posts` 首次请求 200，120 秒内的后续请求 500（`INTERNAL_ERROR`）。
- 根因：`RedisCache.set` 用 `json.dumps(value, default=str)`，pydantic 模型不可序列化 → `default=str` 把**整个模型** `str()` 成字符串存 Redis；`cache.get` 返回字符串 → response_model 校验失败。dev 无 Redis（内存 fallback 存原对象）所以测试永远发现不了。
- 波及面：该端点所有缓存命中；其他 cache.set(模型) 调用点同样暴露。
- 修复：① `app/core/cache.py` 新增 `_json_default`（pydantic → model_dump(mode="json)），全局兜底；② 端点缓存改存 dict + 命中侧 `isinstance(dict)` 门（历史脏键当作未命中重建）。
- 教训：dev/prod 基础设施差异（有无 Redis）会系统性掩盖 bug；"真实使用≈0"让最浅的冒烟（连打两次）都没人做过。
