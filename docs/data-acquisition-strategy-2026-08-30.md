# 数据获取策略调研与对抗式审查（2026-08-30）

> **⚠ 2026-08-30 晚补充：根本重审（kazike 07 号）推翻了本文的原问题定义**，见文末
> [根本重审：数据的根本到底如何弄](#根本重审数据的根本到底如何弄)。
> 本文五大杠杆仍然有效，但它们优化的是"信息流"管道——而实证数据表明那不是对决策价值最高的管道。

背景：现有合规爬虫体系（串行并发=1、全局 1s 限速、白名单、人工审核队列）月产仅 2-3k 条可用数据。
本调研先学同类项目（GitHub/社区），再结合第一性原理给出策略，**先审查后实施**。
调研原始报告含全部来源 URL（RSSHub #2164、wewe-rss、MediaCrawler、changedetection.io、crawl4ai、
OpenJudge、data-as-code 模式等 20+ 项目），要点沉淀如下。

## 第一性原理拆解

基本事实：
1. 高校/政府公告页 90% 是静态 HTML、分布在不同域名——**每个域名 1 req/s 的礼貌性不需要全局串行**。
2. 结构化事实类数据（职位表/分数线/排名）官方都有**批量文件或数据库**，抓 HTML 是最差路径。
3. 公众号/UGC 不逆工程也有通路（微信读书接口/公众号转 RSS 桥）。
4. 我们的结构（RSSHub 已自建 + 质量分 + 审核队列）与业界最佳实践同构，缺的不是架构是**密度与自动化**。

未验证假设（本调研推翻的）：
- "量大就要堆硬件/上 heavy 框架"——错。2C4G 跑 aiohttp 每域并发即可到每秒几十页，crawl4ai 单次 1GB 内存反而是负担。
- "量大=审核人力线性增长"——错。分层自动裁决可把审核成本从 O(条目) 降到 O(来源)。

## 五大杠杆（按 量/投入比 排序）与对抗式审查

### 杠杆 1：按域名并行 + 增量抓取（100-1000x 吞吐解锁）
保留每域 1 req/s，删除全局串行；ETag/Last-Modified 条件请求，列表页只重抓变化。
- **钢人支持**：合规姿态完全不变（域名级礼貌未变），纯代码改动，理论容量百万级 fetch/月。
- **最强反对**：BaseCrawler 是合规核心（SSRF/robots/护栏），深夜动它=把合规引擎当实验场；且现有调度已错峰（02:00/02:30/03:00），当前瓶颈其实在**源数量**而非吞吐。
- **裁决**：采纳，但分两步——先做"每域并发"配置化（ThreadPoolExecutor 按域名分桶，默认关闭）+ 测试覆盖，不动 SSRF/robots 逻辑；等 pytest 全绿+白天窗口再默认开启。

### 杠杆 2：官方批量文件为主结构化来源（已是杠杆 #2 的延续）
国考/省考职位表 xlsx 已落地（import_position_xlsx + yaml 即插即用）✓。扩展面：研招官方数据库
（vendor VanGy-code/postGraduate 的 Scrapy 方案，注意合规审查）、软科 API（已接）、政府开放数据平台 API。
- **钢人反对**：新源=新合规审查成本；路线图 6 周冻结扩源。
- **裁决**：冻结期内不新增源，但 10 月职位表发布日的 xlsx 管道就是本杠杆的最大单点——提前演练 yaml 模板。

### 杠杆 3：公众号/UGC 走 RSS 桥而非爬虫
自建 we-mp-rss/wewe-rss 与 RSSHub 并列，公众号经验帖/公告全走现有 RSS 摄取路径。
- **钢人支持**：公众号是考研经验贴最大富矿，且完全绕开 WAF 对抗；复用 rsshub_research 全链路零新代码。
- **最强反对**：wewe-rss 已归档（2026-05），we-mp-rss 依赖微信读书会话，**登录态=账号风险+维护负担**，会话失效时静默断流。
- **裁决**：进入试点清单但非第一优先；若上，必须配新鲜度告警（data_freshness 已有表）。

### 杠杆 4：CMS 模板化路由扩展 + 长尾 changedetection（RSSHub issue #2164 洞见）
博达 `list.htm`/正方等 CMS 一套模板覆盖数百高校——official_announce 的 DEFAULT_SECTIONS
正是这个形状（detail_url_re + content_cls = 模板描述符）。加一个学校=加一段配置，成本从每站降到每模板。
- **钢人反对**：模板漂移=静默断流（RSSHub 503/404 漂移是常态）；几百校的列表页需人工确认结构。
- **裁决**：采纳为 W1-W2 主攻方向，配套两个护栏：data_freshness 每源监控 + 连续 N 天零产出自动降权告警。

### 杠杆 5：分层自动裁决替代逐条人工审核（O(条目)→O(来源)）
白名单+模板解析 ⇒ 自动发布；其余 LLM judge（OpenJudge/judges 模式）打分；每源历史通过率>95% 自动发，
新源 100% 人工直到 prove；随机 1-5% 抽检校准。
- **钢人支持**：这是杠杆 1-4 的前置——不先做这条，量上来只会淹没审核队列（4001 积压的教训）。
- **最强反对**：LLM judge 引入 LLM 成本与"合成放行"风险（项目红线：真实数据；路线图冻结 LLM 扩展）。
- **裁决**：冻结期内先做**无 LLM 版**——"来源信誉分+模板可信度+质量分≥阈值自动过"三条件全满足才自动发，
  LLM judge 留到解冻后。抽检审计制度化（每周一次 bulk_review 复盘）。

## 根本重审：数据的根本到底如何弄（kazike 07 号，2026-08-30 晚）

### 实证起点（先钉死基本事实，本地库实测）

| 指标 | 数值 |
|---|---|
| 院校库总数 | 616 |
| 有招生目录的院校 | 30（4.9%） |
| 有情报的院校 | 90（14.6%） |
| 有分数线的院校 | 39（6.3%） |
| **四件套全占（目录∩情报∩分数线）** | **29（4.7%）** |

同时：资讯 2314 条、经验贴 1813 条、向量 4976 条——**信息流很宽，决策实体库千疮百孔**。
一个问"云南大学法硕"的用户，在 95% 的院校上拿不到决策所需的任何字段。

### 1. 原方案中只在修补表面的部分

爬虫速度、调度、审核队列、RSSHub 路由、向量库——全部是**信息流层**的优化。
但产品定位是**报考决策器**（北极星=条件完成率+回传率），不是资讯平台。
我们在持续优化一条对决策价值密度最低的管道，同时决策实体库 95% 是空的。
这就是"方案一直在打补丁"的感觉来源：补丁都对，但都补在不重要的墙上。

### 2. 基本事实（无法绕开）

1. 报考决策需要的实体是**有限集**：~900 所院校 × 专业 的 招生目录/考试科目/分数线/报录比，
   加国省考职位表。大部分实体一年只变一次——这不是无限新闻流问题。
2. 数据的两种形态根本不同：(a) 权威结构化事实（官方年度发布，xlsx/官方库）
   (b) 长尾动态信息（公告/经验，持续产生）。两种形态的正确获取方式完全不同。
3. 竞品（研招网/粉笔/中公/知乎）的爬取与内容能力我们永远追不上；**爬取赛道没有我们的位置**。
4. 唯一能产生**别人没有的数据**的来源是用户回传：真实报考结果/进面分数/报录比，
   研招网都拿不到这个粒度。developer2gwy（11k star）整个项目就是社区投稿建成的。
5. 北极星是条件完成率+回传率——**数据战略应该服务北极星，而不是服务"条数"**。

### 3. 从基本事实重新推导的路径

**数据的根本 = 决策实体数据库的字段完整率 + 用户回传闭环。信息流只是触发器，不是资产。**

- **实体库优先**：数据北极星从"月入库条数"改为"**四件套完整率**"
  （Top N 报考热度院校中，目录/科目/分数线/报录比四项齐全的占比）。
  现值 4.7%，目标：W4 前 Top100 院校 ≥80%（报考高度集中于头部，覆盖实际查询的绝大头）。
- **(a) 类数据走官方批量**：职位表 xlsx 管道已是正确答案（gwy_position 20714 行是模范样本）；
  考研侧的"官方批量"=各校招生目录/复试线公告页，**结构化抽取到实体表**（grad_yanzhao_programs/
  grad_scoreline_records），不是抽到资讯流。同样的爬虫能力，目标表不同、度量不同。
- **(b) 类信息流降级为触发器**：2-3k/月足够。它的职责是"发现影响用户决策的公告→推送提醒"，
  不追求量大。已有自动放行让它自转，不再投入。
- **回传闭环是壁垒**：决策卡→"我的结果"回传（decision_review_queue 已有雏形）→
  沉淀往年真实进面分布/报录比。这是唯一正确的"数据壁垒"，也是北极星本身。
  10 月职位表季是回传请求的最佳窗口（用户查职位表=最高意图时刻）。

### 4. 对抗式审查（双向钢人）

**钢人 A（继续扩信息流）**：内容生态带 DAU/SEO/留存，资讯中心已是产品页；
爬取杠杆已验证（RSSHub/自动放行），放弃=浪费已有资产。
最强反对意见：内容赛道竞品碾压且无壁垒，DAU 假设未验证——北极星里根本没有"资讯 PV"。

**钢人 B（实体库+回传优先）**：直接服务北极星与决策器定位；四件套 4.7% 是用户可感知的最大短板；
回传数据构成真壁垒。
最强反对意见：实体采集逐校逐专业**极费人工**（招生目录字段多、格式杂），
Top100 四件套的工作量可能是数月级别，且考研数据有研招网红线约束、官方批量源有限——
这正是当初退到"30 校预置数据"的原因；回传冷启动难，10 月前用户基数小。

**裁决**：B 成立，但必须吸收 A 的两个有效点——信息流不追加投入但也**不关停**（已自转）；
实体采集必须走"**模板化结构抽取**"路线（每 CMS 模板一个抽取器，目标表是实体表），
否则人工不可扩展。适用条件：产品定位保持"报考决策器"不变；若转向内容平台则 A 重新成立。

### 5. 验证第一步（最小实验，非纸面）

1. **把四件套完整率做成可见指标**（data_freshness 或 admin 面板）：当前 4.7% 每周可见，
   让"数据工作"第一次有正确的仪表盘。
2. **单校纵深实验**：选 1 所 Top30 热度院校（如苏州大学），用模板抽取器把
   目录/科目/分数线/报录比补到字段完整——测出"每校真实成本（人时）"，
   用成本 × 100 校推算 W4 目标是否现实，再决定投入力度。
