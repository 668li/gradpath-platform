# Auto Review

结构化代码审查辅助，用于 closeout 门禁检查。

## 何时使用

- 用户要求进行代码审查（code review / autoreview）
- 非平凡的代码修改后，提交/合入/发版前
- 审查本地分支或 PR 分支的修复
- 不用于纯文档或 SKILL.md 变更

## 核心原则

1. **默认输出 P0 阻塞性问题**：仅报告会实质性破坏正常流程、结果或安全边界的问题
2. **审查输出是建议性的**：绝不盲从。每个发现必须核实真实代码路径和相邻文件
3. **拒绝不切实际的边缘情况**：不接受推测性风险、大范围重写、或使代码过度复杂的修补
4. **收敛而非发散**：修复止于当前 PR 范围，不扩展到其他所有者边界

## 范围治理（Scope Governor）

审查前冻结范围基线：

### 三段分类

- **In-scope blocker**：当前 diff 引入、同一所有者边界、无需改变任务合约即可修复
- **Follow-up**：属于相邻 bug 类、兄弟表面、清理或更广泛加固的发现
- **Stop-and-escalate**：需要新协议/配置/存储/公共 API 合约的发现

### 停止修补并报告范围扩展的条件

- diff 超出原始文件数或非测试 LOC 的 2 倍
- 两轮修补后仍未收敛（暂停，重分类剩余发现）
- 最佳修复是"先定义规范合约"而非再加一层本地推断
- 修复后 PR 不再描述同一行为、问题或所有者边界

### 关键例外

仅以下情况可突破范围：**活跃数据丢失、崩溃、安装/升级故障、发版阻塞、具体安全暴露**。

## 审查流程

1. **冻结范围基线**：原始请求、目标分支、意图行为、所有者边界、变更文件、非测试 LOC
2. **运行审查**：列出发现的 P0 问题
3. **核实每个发现**：阅读真实代码路径、相邻文件、依赖文档
4. **分类每个发现**：In-scope / Follow-up / Stop-and-escalate
5. **修补 In-scope 发现**：小修，不重构；修复后重新运行相关测试
6. **两轮后收敛检查**：未收敛则暂停，重分类
7. **输出结果**：清晰的审查结论

## 安全性

- 审查包含安全视角，但不应扼杀合法功能
- 仅当变更创建了具体、可操作的风险或移除了重要安全检查时才报告安全发现
- 对密钥、令牌等敏感信息保持警惕

## 回归溯源

对于发现的 bug，追溯责任：
- 已追溯 PR：记录 blame PR 作者、合入者、当前 PR 作者、PR/日期
- 无可追溯 PR：记录 blame commit SHA、日期、作者用户名
- 自动化合入（如 bots）：尝试找出人工触发者

## 使用方式

```powershell
# 在本地工作区运行
# 审查当前分支相对于 origin/main 的变更
# 输出 P0 级别的阻塞问题
```

## 不要做的事

- 不要为了得到更干净的审查结论而再次运行审查
- 不要把审查变成重写任务的理由
- 不要仅仅为了满足审查者而提交推测性修复
- 不要在范围分类或聚焦证明未解决时堆积/推送审查触发的修复提交
